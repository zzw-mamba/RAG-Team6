# 10 人协作建议

以下是认领席位，不对应真实姓名；请组长在 GitHub Issues 中填写成员与负责人。

| 席位 | 主责 | 主要文件 | 第一项验收 |
|---|---|---|---|
| 1 | 项目协调与集成 | CI、schema、配置、合并 | 全组可 clone、安装、通过 CI |
| 2 | 数据与划分 | data.py、data/ | 实际 ctxs 适配、样本数、固定划分 manifest |
| 3 | 检索与重排 | retrieval.py | BM25 基线与一个有依据的检索改进 |
| 4 | Qwen 回答与服务 | models.py、回答提示词 | 指定 Qwen 的小批真实推理 |
| 5 | 批判循环与停止 | pipeline.py、批判提示词 | 自主停止、轮数上限、格式失败正确区分 |
| 6 | 批判数据与审阅 | training/annotations.py | 同时含有效修正与正确停止的审阅数据 |
| 7 | SFT 训练 | training/sft.py | 可复现 LoRA/QLoRA 试验与适配器 |
| 8 | 强化学习 | training/grpo.py、rewards.py | 真实奖励调用和小规模参数更新日志 |
| 9 | 评测与消融 | evaluation.py、experiments.py | 三组公平对比、纠错/误改、耗时 |
| 10 | Demo、案例与报告 | demo.py、报告材料 | 可展示全过程，成功与失败案例齐全 |

每人至少审查另一模块的一次 PR。席位 1 协调接口，不必独自承担所有公共代码。

## 依赖关系

```text
数据适配 + Qwen接入 + 检索基线
             ↓
        普通RAG与固定验证集
             ↓
批判状态采集 → 审阅 → SFT → 批判修正基线
                                  ↓
                            奖励验证 → GRPO
                                  ↓
                      三组评测 → 案例 → Demo/报告
```

项目框架允许大家先使用 fixtures 并行开发接口；真实效果验证仍要按上述依赖推进。

## 建议建立的首批 Issues

1. 核实完整数据格式、训练样本数和 rationale 质量。
2. 锁定 GPU 环境、模型访问权限和依赖版本。
3. 跑通真实 Qwen 与 LLaMA HTTP/HF 接口。
4. 产出 100–300 条经过双人抽查的批判/停止样本。
5. SFT 试验：输出格式、纠错率与停止质量。
6. GRPO 试验：奖励分布、误改惩罚和冻结回答模型。
7. 固定验证集三组比较与消融。
8. 实时 Demo、失败案例与作业报告。

用仓库 Issue 模板填写，关联 PR；不要把 GPU 日志截图当成完整可复现实验记录。
